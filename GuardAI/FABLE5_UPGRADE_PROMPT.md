## Prompt to paste into Claude Code (Fable 5) — GuardAI full upgrade pass

You are working in the `GuardAI` repo — a Manifest V3 Chrome extension. Its entire pitch is: "GuardAI watches what you type into AI chat tools (ChatGPT, Claude, Gemini, Copilot, Perplexity, and others) and automatically masks sensitive personal/financial data with realistic fakes before it's sent, then restores your real data in the AI's response — so the AI itself never sees your real information. It runs 100% locally, no servers, no accounts."

Your job is to do a full, no-holds-barred upgrade pass: find every bug, close every gap, and make the detection + masking + restore pipeline genuinely production-grade. Don't just patch the first thing you find — treat this as a real audit followed by a real rebuild of the weak spots. Be skeptical of anything that looks "done" until you've personally verified it.

### 1. Get oriented first — don't trust old audit output blindly

There is an existing test harness at `audit.cjs` that runs the real detector + masker against 15 synthetic client records (names, phones, emails, addresses, DOB, TFN/Medicare/licence numbers, account balances) and reports any field that leaks through unmasked. There's also a stale `audit.out` file sitting in the repo from a previous run — **do not trust it**. Files get edited after audits run and nobody re-verifies. Your first step should be:

1. Run `node audit.cjs` yourself right now and read the fresh `audit.out` it generates.
2. Also look at `harness.cjs`, `harness-submit.cjs`, and `bug1-variants.cjs` — figure out what each of these tests, whether they still pass, and whether they're testing anything meaningfully different from `audit.cjs`.
3. Report to me what currently passes and fails BEFORE you start changing code, so we have a real baseline instead of assumptions.

### 2. Codebase map (so you don't have to rediscover this)

- `manifest.json` — MV3 manifest. `content_scripts` inject `src/detector.js`, `src/nlp-detector.js`, `src/masker.js`, then `src/content.js` (in that order, as plain global scripts, not ES modules — they attach to a shared `window.GuardAI` namespace) into a long list of AI chat sites (ChatGPT, Claude, Gemini, Copilot, Perplexity, Poe, Character.AI, Mistral, Groq, HuggingFace, and more).
- `src/detector.js` — the core regex/checksum-based PII detection engine (names, phone, email, address, DOB, TFN, Medicare, ABN, ACN, passport, licence, credit card, BSB, bank account, GPS, money amounts, plus keyword-only categories like health/legal/immigration/confidential/business-confidential/password). Australia-focused formats and checksums (Luhn, TFN mod-11, Medicare check digit, ABN mod-89).
- `src/masker.js` — the reversible real↔fake mapping table (persisted to `chrome.storage.local` only), fake-value generators per data type, and mask/unmask logic.
- `src/nlp-detector.js` — smaller supplementary detector (147 lines) — figure out exactly what it adds on top of `detector.js` and whether it's actually wired in and pulling its weight, or dead weight.
- `src/content.js` — by far the largest file (~2,900 lines). This is what actually runs on the live AI chat pages: intercepting what the user types, showing the "sensitive data detected" review UI, sending masked content, and unmasking the AI's response before the user reads it. This is the part with the most real-world risk because it has to work against DOM structures that differ per-site and can change without notice.
- `background.js` (78 lines) and `popup.js` (201 lines) — service worker and toolbar popup UI.
- `audit.cjs` / `harness.cjs` / `harness-submit.cjs` / `bug1-variants.cjs` — Node-based test harnesses that run the detector/masker logic against synthetic data using `jsdom`, outside the browser.

### 3. Known weak points to specifically dig into and fix

Treat these as required investigation areas, not just suggestions — go verify each one with real test cases, not just a code read-through:

**a. Detection blind spots beyond structured formats.** The current detector is almost entirely regex + checksum based. That's solid for phone numbers, emails, TFNs, Medicare numbers, credit cards, etc., but it will systematically miss sensitive information that doesn't match a rigid pattern — things like "my daughter goes to Lincoln Primary," "we're closing the Henderson deal at $2.3M next week" (only caught if it happens to match the money regex + context keyword), informal addresses, nicknames, or context-dependent business secrets. Write a batch of realistic adversarial test messages (at least 20-30, covering multiple domains: personal, medical, financial, legal, workplace) that a real person might type into ChatGPT, run them through the detector, and find where it silently lets sensitive info through. Fix or clearly flag the gaps — and if some gaps are fundamentally unfixable with regex alone, tell me honestly rather than papering over it.

**b. False positives.** Equally important: find cases where normal, non-sensitive text gets incorrectly flagged/masked (e.g., a random 10-digit number that isn't a phone number, a capitalized two-word phrase that isn't a name, a dollar figure in a recipe or hypothetical). A tool that over-masks will get disabled by users. Build test cases for this too and tune the detectors so precision doesn't get worse while you're improving recall from point (a).

**c. Multi-turn restore robustness.** The whole product depends on the "unmask" step correctly finding fake values in the AI's response and swapping them back to real data. Test what happens across a multi-turn conversation when: the AI paraphrases a fake name/number instead of repeating it verbatim, the AI only repeats part of a fake value, the conversation runs long enough that many real↔fake pairs are active at once, or two different fake values partially overlap as substrings. Find and fix any case where restore silently fails (real data never comes back) or, worse, restores incorrectly.

**d. `content.js` fragility across sites.** Since this one file has to work across ChatGPT, Claude, Gemini, Copilot, Perplexity, and more, check how it detects each site's input box and response elements, and how resilient that logic is. Look for hardcoded selectors that are likely to break if a site changes its DOM, and any per-site special-casing that's inconsistent or incomplete. Given the file is ~2,900 lines, also assess whether it needs to be split into smaller modules (e.g., a per-site adapter pattern) to be maintainable — propose a structure if you think a refactor is warranted, but don't refactor blindly; confirm behavior is preserved with tests before and after.

**e. Error handling & resilience.** Check what happens if `chrome.storage.local` fails, is full, or returns unexpected data; if the detector throws on malformed input; if the masking table grows unbounded over a long-lived browser session (is there any cap/eviction strategy?). Add defensive handling anywhere it's missing.

**f. Test coverage as a real safety net, not just ad-hoc scripts.** Right now `package.json`'s `test` script just errors out ("no test specified") even though there are several working Node-based harness scripts. Consolidate these into a proper, repeatable test suite (a real `npm test` that runs the detector/masker audits and exits non-zero on any leak or regression), and expand it with the adversarial cases from (a) and (c) so future changes can be verified automatically instead of by hand.

**g. Chrome Web Store / privacy readiness.** Review `manifest.json`'s `host_permissions` and confirm every listed site is actually needed and matches what the product claims to support (the landing page FAQ says "ChatGPT, Claude, Gemini, Copilot, Perplexity and more" — the manifest supports a much longer list; decide whether to publicize that or trim permissions to reduce review/trust friction). Check `privacy-policy.html` is consistent with what the code actually does.

### 4. User experience, likability, and visual polish — make people actually want to keep this installed

Detection accuracy is necessary but not sufficient. The single biggest real-world risk to this product isn't a missed regex match, it's a user disabling or uninstalling the extension because it feels annoying, janky, or untrustworthy. Treat "would someone who installs this today still have it enabled and happily using it in three months?" as a real design constraint, not an afterthought, and go through the following:

- **Visual style: clean black and white.** The extension's own look and feel (popup, in-page review card, icons) should be a sharp, minimal black-and-white design — think high-contrast, monochrome, confident and "serious security tool" rather than colorful or playful. Do not reference or match the marketing landing page's styling at all — the landing page is a completely separate, unrelated project and out of scope here. Replace the current plain shield emoji (`&#128737;`) used as the logo in `popup.html` with a proper crisp black-and-white icon/mark, and check that `icons/icon16.png`, `icon48.png`, and `icon128.png` are actually clean and legible at each size (they're currently tiny files — verify they look good at 16px in the toolbar, not just that they exist), consistent with the same black-and-white style.
- **The in-page review UI is the core experience — polish it like it's the whole product.** The actual moment a user interacts with GuardAI is the warning/review card that pops up in `content.js` while they're typing into ChatGPT/Claude/etc. Check that this UI: appears smoothly (no jarring layout shift or flash), is fast enough that it never feels like it's lagging behind typing, is easy to dismiss or act on with a single click or keystroke (not a multi-step chore), and is visually polished in the same clean black-and-white style — not a generic browser alert-box look. If the current implementation is rougher than that, upgrade it.
- **Don't over-interrupt.** A tool that pops a review card for every message, including low-risk or borderline ones, will train users to blindly click through it (defeating the purpose) or turn it off entirely. Make sure "warn only / edit masks / send anyway" style options are real, easy to reach, and that the system is tuned to only interrupt when it's genuinely warranted, with low-friction one-click acceptance for the common case.
- **Make the popup feel alive and reassuring, not static.** `popup.html` already has good bones — a "privacy score" ring, session stats (detected/masked/sent as-is), a recent-swaps log, a platforms-used list, dark/light toggle. Verify all of these actually update live and correctly (not stuck at placeholder values), and consider small touches that make protection feel tangible and rewarding in the moment (e.g., a brief animation or highlight when the score updates or something gets masked) — this is what turns "invisible background tool" into "something the user is glad they installed."
- **First-run experience.** Think through what a brand-new user sees the very first time GuardAI actually masks something for them mid-conversation. If there's no explanation, a user can be confused or alarmed that their own text changed. Add (or improve) a lightweight, one-time first-run explanation of what just happened and why, so the first masking event builds trust instead of confusion.
- **Perceived performance.** Since this sits directly in the critical path of typing into a chat box, any lag will be felt immediately and will get the extension disabled fast. Verify input handling is properly debounced/throttled and doesn't introduce noticeable typing lag, especially in longer conversations where the mapping table and DOM have grown.
- **Accessibility and empty/error states.** Make sure the review card and popup are keyboard-navigable with sensible focus handling, and that empty states (no platforms used yet, no swaps yet, extension freshly installed) and failure states (storage unavailable, detector error) look intentional and on-brand rather than broken or blank.

Weigh every UI change against real detection/masking correctness — never sacrifice accuracy for polish — but treat the "does a normal person like using this" question as equally mandatory, and call out explicitly in your final report what you changed for usability/retention versus what you changed for correctness.
